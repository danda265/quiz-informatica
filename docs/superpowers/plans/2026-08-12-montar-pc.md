# Monte seu PC — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `montar-pc.html`, a self-contained interactive PC-assembly simulator (drag pieces into place, layered error checks, celebration on success), linked from a new card on the quiz-informatica module grid.

**Architecture:** Single static HTML file (`montar-pc.html`), vanilla JS, no build tool, no framework, no Firebase — same pattern as the existing `index.html`/`admin.html`/`ranking.html`. Four screens toggled via `hidden` attribute (safety warning → bench → case → result), a generic Pointer-Events drag engine shared by every piece, and a `PARTS` data object as the single source of truth for names/descriptions/zones.

**Tech Stack:** HTML5, CSS3 (custom properties, CSS animations), vanilla JS (Pointer Events API), inline SVG. No dependencies, no npm, no bundler.

## Global Constraints

- Site has **zero automated tests** today (`index.html`, `admin.html`, `ranking.html` — none have test suites). The approved spec (`docs/superpowers/specs/2026-08-12-montar-pc-design.md`) locks this feature into "arquivo único, sem build tool, sem framework," which rules out adding a test runner just for this feature. **Every task below is verified manually in the browser** (open the file, interact, confirm visually/functionally) instead of via automated tests — this matches the existing codebase convention exactly.
- No Firebase, no `admin.html` changes, no tracking of any kind (spec §2, §3).
- Ordem de montagem é livre com sugestão visual — nunca bloquear o aluno de tentar uma peça fora de ordem (spec §5), exceto a única dependência física explícita abaixo (cooler precisa da CPU já encaixada).
- Painel frontal é 1 conector único — nunca simular pinos individuais (spec §2).
- Peças são ilustração SVG/CSS original — nunca foto (spec §2, §9).
- Linguagem de todo texto voltado ao aluno: simples, adequada a 5º-9º ano (spec §8).
- Reaproveitar a paleta de cores/tipografia do `index.html` (spec §3): `--bg:#f0f4f8`, `--card:#fff`, `--text:#2c3e50`, `--muted:#7f8c8d`, `--border:#d1d5db`, `--ok:#27ae60`, `--err:#e74c3c`, fonte `'Segoe UI',sans-serif`.
- Arrastar deve funcionar com mouse e toque via **Pointer Events** (`pointerdown`/`pointermove`/`pointerup`), sem polyfill — técnica validada ao vivo durante o brainstorming.

## Implementation note not in the spec (flagging, not re-opening scope)

The spec's flow diagram shows Tela 1 → Tela 2 as forward-only, but its own error screen requires a **"Voltar e corrigir"** button that can only work if the student can navigate back to whichever screen holds the still-missing piece — including back to the bench (Tela 1) for CPU/cooler/RAM/M.2, which live only there. So both Tela 1 and Tela 2 get a small `← Voltar` link (same `.back-btn` pattern already used in `index.html`) making navigation bidirectional at any time. This doesn't change what pieces exist or where they go — it's the minimum plumbing needed to make the spec's own "corrigir" button function. Flagging here per plan-writing convention rather than silently deciding it.

- [ ] **Step 1: Add the drag engine (generic, reused by every screen)**

In `montar-pc.html`, inside the `<script>` block, after the `goScreen` function, add:

```js
// ════════════════════════════════════════════
// MOTOR DE ARRASTAR/SOLTAR (Pointer Events — mouse e toque)
// Um único par de listeners globais (pointermove/pointerup), compartilhado por
// todas as peças via `activeDrag` — evita registrar um par novo por peça toda
// vez que renderTray recria a bandeja (o que aconteceria a cada troca de tela).
// ════════════════════════════════════════════
let activeDrag = null; // {pieceEl, tray, correctZones, onLock, onWrong, offX, offY, container}

function setupDraggable(pieceEl, correctZones, onLock, onWrong){
  const tray = pieceEl.parentElement;
  pieceEl.addEventListener("pointerdown", e=>{
    if(pieceEl.classList.contains("locked")) return;
    pieceEl.setPointerCapture(e.pointerId);
    const r=pieceEl.getBoundingClientRect();
    activeDrag = {
      pieceEl, tray, correctZones, onLock, onWrong,
      offX: e.clientX-r.left, offY: e.clientY-r.top,
      container: pieceEl.closest(".card") // só olha zonas da TELA atual (bench ou case)
    };
    pieceEl.style.position="fixed";
    pieceEl.style.zIndex=999;
    pieceEl.style.width=r.width+"px";
    pieceEl.style.height=r.height+"px";
    document.body.appendChild(pieceEl);
    dragMove(e);
  });
}
// Zonas "candidatas" a receber uma peça: visíveis (sem [hidden]) E ainda vazias
// (sem peça .locked dentro). Sem o segundo filtro, z-cooler nunca recebe o cooler:
// como ela nasce nas MESMAS coordenadas de z-cpu e vem depois no HTML, uma vez que
// a CPU trava dentro de z-cpu, qualquer solto naquele ponto da tela "acha" z-cpu
// primeiro (find() pega o primeiro match em ordem do DOM) e nunca chega a testar
// z-cooler — mesmo com z-cooler já visível.
function openZones(container){
  return Array.from(container.querySelectorAll(".drop-zone:not([hidden])"))
    .filter(z => !z.querySelector(".locked"));
}
function dragMove(e){
  const {pieceEl, offX, offY, container} = activeDrag;
  pieceEl.style.left=(e.clientX-offX)+"px";
  pieceEl.style.top=(e.clientY-offY)+"px";
  const pr=pieceEl.getBoundingClientRect();
  openZones(container).forEach(z=>{
    const zr=z.getBoundingClientRect();
    const over = pr.left<zr.right && pr.right>zr.left && pr.top<zr.bottom && pr.bottom>zr.top;
    z.classList.toggle("hover", over);
  });
}
document.addEventListener("pointermove", e=>{ if(activeDrag) dragMove(e); });
document.addEventListener("pointerup", ()=>{
  if(!activeDrag) return;
  const {pieceEl, tray, correctZones, onLock, onWrong, container} = activeDrag;
  activeDrag = null;
  const pr=pieceEl.getBoundingClientRect();
  const zones=openZones(container);
  const target=zones.find(z=>{
    const zr=z.getBoundingClientRect();
    return pr.left<zr.right && pr.right>zr.left && pr.top<zr.bottom && pr.bottom>zr.top;
  });
  zones.forEach(z=>z.classList.remove("hover"));
  if(target && correctZones.includes(target.dataset.zone)){
    // reancora a peça DENTRO da própria zona (não em document.body) para que ela
    // suma/apareça junto com a tela — .drop-zone já é position:absolute, então
    // vira o container de posicionamento do filho abaixo. Não apagamos o texto-label
    // da zona (ex. "CPU") — a peça, absoluta e centralizada, cobre visualmente o
    // texto, e isso deixa o reset trivial: remover a peça basta pra reexpor o label.
    target.appendChild(pieceEl);
    pieceEl.style.position="absolute";
    pieceEl.style.left="50%";
    pieceEl.style.top="50%";
    pieceEl.style.transform="translate(-50%,-50%)";
    pieceEl.style.zIndex="";
    pieceEl.classList.add("locked");
    onLock(target.dataset.zone);
  } else if(target){
    pieceEl.classList.add("shake");
    if(onWrong) onWrong(target);
    setTimeout(()=>{ pieceEl.classList.remove("shake"); returnToTray(pieceEl,tray); },480);
  } else {
    returnToTray(pieceEl,tray);
  }
});
function returnToTray(pieceEl,tray){
  pieceEl.style.position=""; pieceEl.style.left=""; pieceEl.style.top=""; pieceEl.style.zIndex="";
  tray.insertBefore(pieceEl, tray.firstChild);
}
```

`setupDraggable`'s own signature and every call site are unchanged (still `(pieceEl, correctZones, onLock, onWrong)`) — this refactor is internal. Each piece still gets its own `pointerdown` listener (harmless: pieces are freshly created per `renderTray` call and garbage-collected once detached with no other references), but there is now exactly one `pointermove`/`pointerup` pair for the whole page's lifetime instead of one new pair leaking in on every screen visit.

While a piece is being dragged it's temporarily reparented to `document.body` with `position:fixed` so it can follow the cursor anywhere on screen — that part is intentional. What matters is where it ends up: a **locked** piece gets moved into its `.drop-zone` (a real child of `#bench-board`/`#case-box`, inside that screen's `.card`), so `hide()`-ing the screen naturally hides it too. A piece that bounces back goes into the `.tray` (also inside the screen's `.card`). Neither case leaves an orphaned element floating in `document.body` — if you skip this and leave a locked piece `position:fixed` in `document.body`, it will stay visible on top of every other screen (including after `resetAll()`), since hiding a `.card` via the `hidden` attribute has no effect on fixed-positioned elements that live outside it.

`openZones` is why the CPU→Cooler sequence actually works end to end: right after CPU locks into `z-cpu`, `z-cooler` is unhidden by `handleLock` (Step 2 below) at the *same screen coordinates* `z-cpu` occupies. Without filtering out already-occupied zones, a drop aimed at that spot would keep resolving to `z-cpu` (first match in DOM order) forever, and the cooler could never be placed — this was caught by actually dragging CPU-then-Cooler in a real browser, not by reading the code.

  for(let i=0;i<40;i++){
